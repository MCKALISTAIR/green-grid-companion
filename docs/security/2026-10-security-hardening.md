# Security hardening (Oct 2026): rollout runbook (Lovable Cloud)

GridSense runs on **Lovable Cloud** (project `1558020f-8a4c-43dc-9ea0-79533f5d485c`,
Supabase ref `klwezcjmlrdwvvzisdtd`). The rollout is built so that the
**Lovable agent does all the work**. Alistair only approves its prompts. Nobody
needs a terminal, `curl`, `openssl` or the Supabase CLI.

## What needs no manual work (and why)

| Concern | How it's handled |
|---|---|
| Cron/scheduler secret | **Generated by the migration inside the database** (Supabase Vault entry `cron_secret`, with a fallback to `private.scheduler_secret` if Vault is unavailable). pg_cron reads it with `public.get_scheduler_secret()`. Edge functions read it through the same RPC using the service role; the RPC is executable by `service_role` only. There is **no `CRON_SECRET` to create and no Vault entry to add by hand**. |
| Tampered `app_config.supabase_url` | The migration resets it to `https://klwezcjmlrdwvvzisdtd.supabase.co` as its very first statement, before anything uses the secret. |
| Encrypting existing plaintext Octopus keys | Automatic. `check-carbon-intensity` runs every 30 min and encrypts any remaining legacy rows (in batches; idempotent; once nothing is left it costs one cheap query). Keys are also encrypted the first time they're used. The agent can trigger a run immediately (see message 2). |
| Functions deployed before the migration is approved | Supported. Credential reads and writes fall back to the legacy columns, so users keep working exactly as before. Scheduler endpoints answer 503 "not ready" and never crash; the old cron jobs send no secret, so they are rejected until the migration lands. Notifications pause for that window only. |

Why a DB-generated secret instead of a `CRON_SECRET` env var mirrored into Vault:
- Only one copy exists, so the two sides can never drift.
- The value never passes through a person, a chat, or an edge function log.
- It doesn't depend on any function cold start having run first.
- A caller who can run `get_scheduler_secret()` already has the service role key, so no new capability is exposed.

## Rollout (Alistair's part: 3 approvals)

### (a) Before merging: add one secret
Send **Lovable message 1** (below). Lovable shows its secure secret form. Paste a
**64-character random password** (letters + digits) from your phone's password
manager, or use Lovable's generator if it offers one. Save the value in the password
manager too: if it's lost, users have to re-enter their Octopus keys.

`OCTOPUS_CREDENTIALS_KEY` accepts any random string of 32+ characters (a
256-bit key is derived from it with HKDF-SHA-256) or a base64 32-byte key.

If you merge before adding it, nothing breaks for existing users. New Octopus
connections fail with "temporarily unavailable" until the secret is added.

### (b) Merge PR #31 on GitHub
Lovable syncs `main` and deploys the edge functions. If they deploy before the
migration is applied, that's fine (see the table above).

### (c) Ask Lovable to apply the migration and run the checks
Send **Lovable message 2**, approve the migration prompt, then let it run the
read-only checks and the one-off encryption trigger.

### (d) Checks
- Lovable's report shows every check as expected (listed in message 2).
- Open the app: Octopus still shows as connected, with "API key ending ••••xxxx".

Optional, a few days later: **Lovable message 3** (forbid plaintext permanently).

Ship new iOS/Android builds when convenient. The client no longer stores keys,
and the new build removes keys that old builds cached on devices.

## Lovable messages

**Message 1 (before merge)**
> Please add a new Supabase edge function secret named `OCTOPUS_CREDENTIALS_KEY` using your secure secret form. I'll paste the value myself. Don't generate code or change anything else.

**Message 2 (after merging PR #31 and syncing)**
> PR #31 (security hardening) is merged. Please do the following and report the results. Don't change any code or SQL.
> 1. Apply the database migration `supabase/migrations/20261003120000_security_hardening.sql` **exactly as written** (no edits, don't regenerate it).
> 2. Make sure these edge functions are deployed from the latest `main`: `octopus-energy`, `check-carbon-intensity`, `daily-forecast`, `weekly-digest`, `monthly-report`.
> 3. Trigger the legacy Octopus key encryption once by running this SQL (it calls the scheduler endpoint with the database-held secret; the secret is never shown):
>    ```sql
>    select net.http_post(
>      url := (select value from public.app_config where key = 'supabase_url') || '/functions/v1/check-carbon-intensity',
>      headers := jsonb_build_object('Content-Type', 'application/json', 'x-cron-secret', public.get_scheduler_secret()),
>      body := '{}'::jsonb
>    );
>    ```
> 4. Wait about 30 seconds, then run these **read-only** checks and paste the results (don't print any secret values):
>    ```sql
>    select key, value from public.app_config;
>    select (select count(*) from public.octopus_credentials where api_key is not null) as plaintext_keys,
>           (select count(*) from public.octopus_credentials where api_key_encrypted is not null) as encrypted_keys;
>    select jobname, schedule, command like '%get_scheduler_secret%' as sends_secret from cron.job order by jobname;
>    select public.get_scheduler_secret() is not null as scheduler_secret_present;
>    select id, status_code, left(content::text, 200) as body, created from net._http_response order by created desc limit 5;
>    select tablename, policyname, roles, cmd from pg_policies where schemaname = 'public'
>      and tablename in ('app_config','geocoding_cache','octopus_credentials','rate_limits','scheduled_notification_log') order by 1, 2;
>    select table_name, grantee, privilege_type from information_schema.role_table_grants
>      where table_schema = 'public' and grantee in ('anon','authenticated')
>      and table_name in ('app_config','geocoding_cache','octopus_credentials','rate_limits','scheduled_notification_log') order by 1, 2, 3;
>    select grantee, column_name from information_schema.column_privileges
>      where table_schema = 'public' and table_name = 'octopus_credentials' and grantee in ('anon','authenticated') order by 1, 2;
>    select p.proname, has_function_privilege('anon', p.oid, 'execute') as anon,
>           has_function_privilege('authenticated', p.oid, 'execute') as authenticated,
>           has_function_privilege('service_role', p.oid, 'execute') as service_role
>      from pg_proc p join pg_namespace n on n.oid = p.pronamespace
>      where n.nspname = 'public' and p.proname in ('fn_check_rate_limit','get_scheduler_secret','get_my_credentials_status');
>    ```
> 5. Check the latest `check-carbon-intensity` and `octopus-energy` edge function logs for errors and summarise them.

Expected results:
- `app_config` contains only `supabase_url = https://klwezcjmlrdwvvzisdtd.supabase.co`.
- `plaintext_keys = 0` (if not yet, the next 30-minute run finishes it).

- The latest `net._http_response` row is `200` and its body contains `"legacy_credentials":{"status":"done",…}`.

## Rotating the scheduler secret (rare)
Ask Lovable to run:
```sql
select vault.update_secret((select id from vault.secrets where name = 'cron_secret'),
                           replace(gen_random_uuid()::text || gen_random_uuid()::text, '-', ''));
```
(or `update private.scheduler_secret set secret = …` if the Vault fallback was used).
Edge functions pick it up within 5 minutes (per-instance cache).
